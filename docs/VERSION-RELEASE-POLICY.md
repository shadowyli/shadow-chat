# 逐版本交付规则

每个对外交付版本必须同时保留可追溯源码和 Windows 安装包。测试版使用
`v<版本>-test` 标签和 GitHub prerelease；正式版本使用 `v<版本>`。
版本标签、已发布安装包与 Release 附件不得覆盖，修订使用新版本号。
自 1.1.1 起采用强制更新策略：客户端启动及运行中复查最新发布版本，旧版不得
进入或继续聊天；校验失败不能跳过。分发清单必须写入 `mandatory: true`。
已交付的旧客户端无法靠修改清单获得尚未实现的拦截能力，需先人工升级一次。

## 发布流程

1. 检查工作区修改归属、仓库规则、版本号和已存在的远程标签。
2. 审查待提交文件。不得包含凭据、账号数据、聊天记录、附件、明文恢复资料、
   临时文件和本机构建输出。负责人恢复配置按现有安装机制使用加盐哈希。
3. 构建客户端并运行相关回归，再生成安装包，验证安装、覆盖升级与外部资料保留。
4. 在工作分支提交完整源码、资源、构建脚本、测试和文档，推送并创建 PR。
   不自动合并受保护分支，不强制推送。
5. 为已验证的源码提交创建版本标签。发布信息记录完整 commit、构建环境、
   验证结果、程序及安装包的 SHA-256。
6. 发布 GitHub Release。至少包含 Windows 安装包、SHA256SUMS.txt、
   build-info.json 和发布说明；对应标签提供 GitHub 自动源码归档。
7. 将同一安装包暂存到 FlowX，更新版本清单和版本记录。逐项核对版本号、
   文件大小和 SHA-256；部署公司环境前明确实际部署范围。
8. 检查远程分支和标签、Release 状态与附件，下载远程安装包并核对完整哈希。

强制更新客户端投入试用前，必须先部署可访问的公司版本清单、下载页和安装包。
GitHub Release 发布不等于 FlowX 内网版本服务可访问。清单不可用时，按强更规则
阻塞客户端并提供重试，不得把这种状态表述为已经具备办公环境可用性。

主 agent 负责协调、复核和统一汇报，构建／发布子代理负责构建及安装验证。
集成工具不可用时使用 `git` 与 `gh` CLI；登录或权限失败须保留成果并报告，
不得绕过分支保护。

`packaging/launch_installed_review.py` 与 `close_review_process.py` 是开发审查辅助
工具，仅用于显式启动和关闭隔离的安装测试程序，不属于安装包 payload。

## 构建信息

`build-info.json` 至少包含 product、version、channel、sourceCommit、sourceTag、
构建环境、安装包文件名/大小/SHA-256、程序 SHA-256、验证结果及限制。
该文件作为 Release 附件生成，避免在源码提交中自引用尚不存在的 commit。

## Release 说明与包体说明

每个 Release 都要明确列出新增、改进、修复、适用系统和架构、安装与升级步骤、
数据保留规则、验证范围、已知限制及待验证事项。不要只填写版本号或“更新优化”。
列出各附件的文件名、用途、精确字节数和 SHA-256 校验方法，让使用者能区分
安装包、源码包、构建信息和校验清单。说明包体变化时以实际文件清单为依据，
不能仅凭体积增减推断功能或运行库是否完整。

## 历史版本

不得把当前源码追认成旧安装包的源代码。如果历史安装包没有对应源码提交，
应保留已有文件与验证记录并说明追溯缺口，不补造标签或构建证据。

## 验证边界

同机多进程测试不能证明真实办公网络通过；本机安装不能证明所有企业权限
与 Windows 版本通过。发布说明必须保留这些限制，现场验收继续单独记录。
